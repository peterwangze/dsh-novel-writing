# Novel Studio（小说工作台）

dsh-novel-writing 插件在浏览器侧提供两个可视化入口，本文约定你（Coordinator）与它们的协作方式。

## 入口

- **会话顶部「小说」标签**（conversation.view `novel-studio`）：完整工作台。
- **侧栏「小说 HUD」**（sidebar.footer.action + shell.overlay）：浮动实时状态面板（当前小说、阶段、章节/字数、发布/变现门禁、最近更新时间），3s 轮询。
- **设置 → 小说写作**：工作区根目录、轮询周期、API 访问控制、各平台发布模式与命令。

## 工作台布局

| 区块 | 内容 | 谁写 |
|---|---|---|
| 顶部操作条 | **＋ 新建小说**（目录名+书名 → 创建；可「创建并开始工作流」）、**▶ 开始/继续工作流**（把启动/续传指令注入当前对话）、**文件树开关**、页签（章节/工作流/数据/发布/请求） | — |
| 左侧栏·书目 | workspace 下全部书目（标题/阶段/章数/待处理请求角标），点击切换 | — |
| 左侧栏·文件树 | 当前书目 `novel-project/` 完整目录树（可折叠）；点击文件就地预览（.md 渲染，其余原文本；>512KB 提示外部打开） | 你写项目文件，工作台读 |
| 章节页 | 左：章节列表（字数/已发布/门禁⚠）；中：阅读（Markdown 渲染，`---` 分场景）或编辑（textarea） | 你写 `novel-project/07-content/`，工作台读 |
| 工作流页 | 当前阶段、完成阶段清单、门禁开关（发布/变现/AI路径/偏离度）、请求列表 | 你写 `workflow-state.json`，工作台读 |
| 数据页 | 信号列表（严重度/阈值/建议行动）、指标录入表单（每日一行） | 工作台写 `11-data-monitoring/metrics.json` |
| 发布页 | 平台选择、导出/导出+命令/仅清单、发布记录 | 工作台写 `dist/<平台>/` 与 `.dsh-plugin/publish-log.json` |
| 请求页 | 用户提交的请求（优化章节/审查/发布/数据/人工）+ 完成按钮 | 工作台写 `18-requests/*.json` |

## 启动/续传指令的形态

工作台「▶ 开始/继续工作流」按钮会把下面这类消息直接注入当前会话并提交（新书目=开始，已有进度=续传；按钮按 `completed_stages`/章数自动判断）：

```
开始小说创作工作流：《法医仙途》（目录 fayi-xiantu）
继续小说创作工作流：《法医仙途》（目录 fayi-xiantu）
```

**预设按需加载**（不修改全局默认预设；仅在用户从工作台触发写作逻辑时挂载）：
- 会话已在 novel-writing 预设 → 直接注入指令；
- 会话还是 blank（尚未说过话）→ 先经 `agentPresets.select` 把本会话切到 novel-writing 再注入（宿主只允许 blank 会话切换）；
- 会话已开始且用其他预设 → 预设锁定不可切换；自动新开本工作区专用会话（挂载 novel-writing 预设 → 转场 → pendingLaunch 通道自动发送启动指令；若未自动发送，新会话「小说」标签会出现「▶ 发送启动指令」按钮）。

你收到该形态消息时：按 using-writing-workflow 主 Skill 处理——`novel_list`/`novel_status` 确认该目录存在，然后从 `work_type_selection`（新）或 `workflow-state.json` 断点（旧）继续；目录名即书目 id。新建但未开始的书目 current_stage 为 `work_type_selection` 且无章节。

## 与你的协作契约

1. **实时渲染**：工作台按设置轮询（默认 2s，设置可调且实时生效）；你在 `novel_chapter_write` / fs 写正文后，工作台自动重渲染，无需通知。
2. **编辑保存**：用户在编辑框改稿（Ctrl+S 或保存按钮；切章/退出编辑有未保存确认）→ 走同一个 `saveChapter` 门禁（未通过即拒绝，可"强制保存（人工改稿）"并打 `forced` 标记）。你在读取章节时应检查 `forced`，将其视为「用户手工改过，需要重新走审查与 ledger」的信号。
3. **请求队列**：用户从工作台提交 `optimize/review/publish/data/manual` 请求。你在每个工作阶段开始（或用户说"处理工作台请求"）时调用 `novel_requests` 取未处理请求，处理完 `novel_request_done` 标记。请求本身就是人与 AI 的高价值协作点：它们携带用户意图，优先于你的自主安排。
4. **数据录入**：工作台表单写指标（完读率/读完率/追读/日增收藏/收益，含最近 7 天记录表），宿主算信号；你也可以用 `novel_data_ingest` 批量入库（records 数组，或 platform=… 执行该平台 fetchCommand 适配器——用户说「抓取番茄数据入库」即此路径）。
5. **不要替用户做决定**：工作台只提供信息与入口；方向性决策（改大纲、改书名、重写章节）仍走 `ask_user_question`。
