### F1 — 回滚方案未演练（硬门槛 H2 FAIL）｜严重度 **P1**
- **现象**：方案完备但从未在测试环境执行过一次往返。
- **证据**：`rollback-plan-0.5.2.md` §6 L78「已在测试环境实际演练 ⚠️ **未执行** …… 不主张已验证」；`release-notes` §4.1 L77；`release-checklist-0.5.2.md` §C.2 L36【文档】。
- **影响**：回滚路径 A/B/C 的命令正确性与幂等性均未实证；若发布后发现安装面异常，回退动作本身将成为「未验证的操作」。**但**：回滚对象为本地 tag/安装版本（非运行态系统），且本版未 push ⇒ 无生产面、无用户可见面，实际风险敞口低（K3 待验证：`install.ps1` 幂等性证据来自 BUG-006 交付的隔离实测，其对象 ≠ 被发布树）。
- **修复建议**（二选一，须留痕）：① **补一次隔离演练**——在 `%TEMP%` 隔离根 + `DSH_HOME`/`npm_config_*` 重定向下执行路径 A 往返（`checkout v0.5.2 → install → checkout v0.5.1 → install → 回 v0.5.2`）并记录原始输出；② 由 Coordinator 走**显式风险接受**（关键决策，需用户确认）并在 `decision-log` 落条 + 清单 §C.2 改写为「不适用（非运行态对象）· 已接受风险」，附观察窗（push 后用户侧首次安装前）。

### F2 — push 未执行；且 push 范围含未发布的 v0.6.0 线工作（可见面变化未显式声明/授权）｜严重度 **P1**
- **现象**：(a) 发布提交与 `v0.5.2` tag 仅在本地，远端 `origin/main` 仍 = `3442f396`，用户**无法通过远端获得 v0.5.2**；(b) 建议动作 `git push origin main v0.5.2` 会把**本机领先远端的 44 commits**（含 COMPAT-002~016 全部 v0.6.0 线工作）一并推上远端主线。
- **证据**：`release-notes` 头 L5 + §7 R1 L116 + §9-1 L172【文档】；【C】本地 tag 存在/未 push、远端 main = `3442f396`、领先 44 commits、远端无该 tag。

## 4. tag 边界与范围口径判断（专门裁决）

**问题**：`v0.5.2` tag 指向版本 bump 提交 `e1f25df8`（与 v0.3.0/v0.4.0/v0.5.0/v0.5.1 四个历史 tag 的惯例一致），因此补建的三件 `docs/release/*` **不在 tag 树内**（在其后的 `e093e72`）；同时 tag 树因本机领先远端 44 commits 而含 v0.6.0 线（COMPAT-002~016）内容。

**判断（四条）**：

1. **边界本身是否可接受**：**方向可接受，状态不可接受（须处置）**。「tag 指向发布提交（含版本 bump）」是仓库**既定惯例**（4 个历史 tag 同构），方案 A 的选择**有据、非失误**；且方案 B（tag → `3442f39`）会导致「checkout v0.5.2 得到 version 0.5.1」的更严重误导——**方案 A 优于方案 B 的论证成立**（`release-notes` §3.1 L47-48）。
2. **是否需重定 tag**：**需处置，但本 Reviewer 不建议重定到 `3442f39`**。「范围 = BUG-006 代码面」与「tag 树内 version = 0.5.2」在当前线性历史上**不可兼得**；重定到 `3442f39` 会以牺牲版本一致性换取范围精确性——**以更严重的错误替换较轻的错误，不采纳**。可行选项按优先级：① **重定至 `e093e72`**（消除「工件不在 tag 树内」这一**可机器观测**的不一致，成本为零，范围仍以声明承担）；② 在 `3442f39` 之上重建发布提交后重打 tag（同时满足范围与版本一致性，但需改写本地未推送历史 + 重新生成记录 SHA）；③ 保持现状 + 用户显式确认。**三选一必须留痕**。
3. **口径本身的效力边界（重要）**：现口径「v0.5.2 代码范围 = BUG-006 安装通道适配；COMPAT-* 属未发布 v0.6.0 线」仅存在于**声明面**（`release-notes` §1.1 + §3.2 + 路线图行 + `checklist` §B 分层机检）。**声明面不可机检**——任何下游消费者若改用 tag 树/工作树作判据，即会偏离。因此口径**有效但不自证**：必须由 §3 的处置把「tag 树 ↔ 声明」差距**缩小到可机器核对**（至少消除「发布工件缺失」这一条）。
4. **未 push 使一切可逆**：tag 与发布提交均未 push（远端 main = `3442f396`，远端无该 tag）⇒ 复议、重定、甚至整体重做**零远端副作用**。这**降低**了本 finding 的紧迫度（故为 P1 而非 P0），但**不消除**——一旦按现状 push，边界即固化，此后修正须走 revert + 新版本号。
