## 三、P1-1 修复的实质验证（协议重点 2）

**修复实现**（client.js:2710）：`style: novels.length >= 1 && novels.length <= 2 ? { gridTemplateColumns: 'repeat(auto-fit,minmax(320px,420px))', justifyContent: 'center' } : undefined`；类模板（3623）`repeat(auto-fill,minmax(320px,1fr))` **零改动** ✓（smoke.mjs:568/1143 正断言锁两分支差异）。

**轨道数学验证**（容器宽 W，gap 20px；auto-fit = auto-fill + 空轨塌缩，轨宽 [320, 420]）：

| 场景 | 网格项数 | 轨道数 n=⌊(W+20)/340⌋ | 轨道组宽 | justify-content:center 效果 |
| --- | --- | --- | --- | --- |
| 1 本+磁贴，W≥1040（如 1400×900 屏 → W≈1088） | 2 | 3，塌 1 → 2 | 2×420+20=**860** | **✅ 真居中（自由空间 ≥180px 可见）** |
| 1 本+磁贴，860≤W<1040 | 2 | 2 | 860（轨到 420 上限封顶） | ✅ 居中（自由空间 W−860 > 0） |
| 1 本+磁贴，W<860（用户实测 1078×593 → 控制台内容宽 ≈766） | 2 | 2 | W（轨 373 < 420 上限） | ◯ 无居中——但 2 项填满行宽、本就无右侧空白，**无缺陷场景** |
| 2 本+磁贴，W∈[766,1300) | 3 | 2–3，全被占 | W（轨 320~420 未封顶） | ◯ 无居中——但 3 项填满行（或行 2 磁贴左置），**无「稀疏空白」缺陷**；W≥1300 时轨封顶/塌轨 → 居中生效 |
| ≥3 本 | ≥4 | auto-fill 1fr | W | 分支不应用（undefined）→ 类模板即标准满幅（✅ 零改动） |

**验证结论**：Developer 声称「auto-fit 轨道组 ≤860px < 容器宽 → 自由空间存在」**在真实缺陷场景（1 本+磁贴，W≥860）成立、居中可见生效**；「无效果」区域恰好是「轨道被项填满、无稀疏空白」的区域（即修复前就无视觉缺陷的区域）——**P1-1 判定为已修复（防「修复只改了断言没改行为」复查通过）**。不等式说明：smoke 目前仅断言源码字符串（1142）非计算样式，缺陷场景的视觉效果建议由 Coordinator 双主题探针截图目检（现有交付验证流程）覆盖，另注 P3 精确性备注（见四.3）。

## 四、新引入 & 副作用检查（协议重点 3/4）

### 4.1 【P0-0 新引入回归】0 本书已加载态：网格+磁贴未隐藏，与英雄空态并存

- **位置**：`lib/client.js:2708-2710`（grid 渲染分支门控）。
- **R1 原代码**：`novels.length === 0 ? null : el('div', { className: 'nv-cgrid', ... })`——0 本隐藏网格 ✓。
- **R2 现代码**：`poll.data === null ? null : el('div', { className: 'nv-cgrid', ... })`——P1-2 修复时把门控条件**整体替换**（而非追加）。已加载 0 本书（`poll.data !== null && novels.length === 0`，即真实空工作区新用户）时：hero 渲染（2691 `poll.data !== null && novels.length === 0` ✓）+ **grid 同时渲染**（2708 只判 poll.data）→ 空网格（`shownNovels=[]`）中带 ＋磁贴（2740）——**「0 本书隐藏网格与＋磁贴」规格被违反**，且 hero 主 CTA「＋ 新建小说」与磁贴 CTA 重复呈现。
- **规格依据（可复查）**：DEC-022 ①（L30：「0 本书主区居中英雄…隐藏网格与＋磁贴」）；README.md（「0 本书为英雄空态…隐藏网格/磁贴」）；CHANGELOG UX-055 条目（同文）；R1 报告已确认该行为为 V1 委托之一。
- **为什么 smoke 144/144 未捕捉**：ux008（smoke.mjs:518）mock 现为 `poll.data=null`（加载中）→ 仅断言「加载中 hero=0/empty=0/grid=0」；R1 的「0 本书 → grid 隐藏」渲染树断言被改成了加载中语义，**「已加载 0 本 → hero=1 且 grid=0」再无任何断言**（ux055③⑥ 1133-1147 亦无）；`clsCount['nv-cgrid']` 的 `grid:0`（562）只覆盖加载态。断言语义迁移是回归漏检的直接原因。
- **影响**：空工作区首次打开控制台（新用户 0 本书的**默认场景**）视觉呈现错误（hero 与磁贴并存、重复 CTA）；功能未损（两条创建通道均可点）。
- **级别裁定**：P0（逻辑错误/规格违反——分支条件错误导致行为与已批准规格不符；且 0 本为常见态而非边角）。
- **修复建议**：2708-2710 门控恢复 0 本排除：`poll.data === null ? null : novels.length === 0 ? null : el('div', { className: 'nv-cgrid', ... })`（或合并为 `poll.data === null || novels.length === 0 ? null : ...`——保持与 2691/2699 同构）；**并补断言**：a) 源码级——该双门控字符串入 ux008/ux055③⑥；b) 渲染树级——若 smoke mock 支持注入「已加载空数据」（`poll.data={overview:{novels:[]}}`），新增「0 本已加载 → nv-hero=1 且 nv-cgrid=0」；若不支持，至少在 ux008 补「已加载 0 本」分支的判据或将 mock 机制扩展（Developer 判断最小可行面）。

### 4.2 P1-2 门控副作用评定（协议重点 3）—— 可接受

- 加载中（`poll.data===null`）三分支均不渲染（2691/2699/2708）→ 主体留白；工具行（排序按钮 ×2 + apiError/notice 行，2677-2682）、底部搜索行（2749+）维持——与 ux008 断言一致（560-563）。
