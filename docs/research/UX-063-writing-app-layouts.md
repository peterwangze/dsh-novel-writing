## 0. 结论先行（TL;DR）

1. **当前问题不是“配色不够好”，而是优先级倒置 + 导航面过多。** 仓内 1600×900 真机截图实测：正文可视宽度约 **200px（约 13 个汉字/行）**，宿主对话窗约 **660px**；2400×900 下正文约 470px、对话约 1270px。写作面是全屏里最窄的区域，对话窗是最大的区域 [L7][L8]。
2. **同类产品普遍收敛为「一个结构树 + 一个正文面 + 一个上下文面板」**，并在写作时让 chrome 退后：Scrivener 的 binder/editor/inspector + Composition Mode、Ulysses 的 Library/Editor + Focus、novelWriter 的 Project Tree/Document/Outline、Novelcrafter 的 Codex/Editor/Chat、Manuskript 的 Outline/Editor/Story Bible [S1][S2][S5][S9][S15][S33][S44][S45]。
3. **发布在成熟产品里是独立的、多步的流程**（Compile / Publishing / 平台审核），不是内容区下方的一排按钮：Scrivener Compile、Ulysses Publishing、Obsidian Longform Compile、番茄/阅文的“发布→审核” [S2][S8][S12][S47][S52][S53]。我们当前发布面板是“平台下拉 + 含已发布勾选 + 3 个模式按钮”，且**不能逐章选择**（代码事实：UI 一次性提交全部未发布章；服务端 `/publish` 本身支持 `chapters` 子集，是纯 UI 缺口）[L5]。
4. **进度/目标应当是独立信息层，而不是卡片上的两个数字。** Ulysses 有 Dashboard + Goals、LivingWriter 有 Goals + Stats、番茄作家助手有数据看板；我们的管理台只有书卡网格，1600×900 下约 70% 是空白 [S6][S7][S31][S47][L9]。
5. **中文连载场景需要改造 4 件事**：日更/存稿/断更进度、平台合规门禁、多平台发布清单、中文排版预设。**不需要**：竖排、EPUB/印刷编译、英文语法检查（详见 §4）。
6. **三个方案都能在单文件客户端实现**；推荐 **B 的首屏（仪表盘）+ A 的写作视图（三段式）**，分阶段落地。核心链用户动作从 **9 步降到 5~6 步**，页签切换从 **3 次降到 0 次**（口径见 §5.0）。
7. **上一轮（A+B）失败的判据要写进本轮验收**：只改了令牌/对比度/±1px，没有改“首屏轮廓、区域优先级、任务流”。本轮验收必须用：首屏三问、正文可视宽度、核心链步数、与旧截图并排可指出的 5 处结构差异（§6.2/§6.4）。

### 1.4 关键发现：正文被挤到全屏最窄（截图实测）

| 视口 | 左侧文件树 | 章节列 | 正文可视 | 宿主对话窗 | 正文约每行汉字（15px 估算） |
|---|---:|---:|---:|---:|---:|
| 1600×900 [L7] | ~280px | ~140px | **~200px** | ~660px | ~13 字 |
| 2400×900 [L8] | ~230px | ~110px | ~470px | ~1270px | ~31 字 |

- 1600×900 是常见笔记本视口；此时正文只占全屏宽度约 **12.5%**，对话窗约占 **41%**。2400×900 下正文仍不到 `34em`（510px）的满宽，对话窗约占 **53%** [L7][L8]。
- **口径说明**：表中的“每行汉字”按当前 15px 正文字号估算；截图拍摄时的字号可能更小，实际每行字数可能更多。核心结论是**宽度占比与“正文最窄”**，不依赖字号。
- 左侧同时存在 **文件树 + 章节列 + 页签 + rail** 四个导航/状态面；写作时真正需要的“当前章正文 + 门禁/信号 + 对话”被拆在四个区域。
- 这解释了“上一轮改了很多但感知提升不大”：**首屏的空间分配没有变，用户每天面对的仍是“窄正文 + 大对话 + 多入口”** [L7][L8][L9]。

**现状结构示意（1600×900 截图近似，非精确几何）**：

```
┌ 宿主侧栏 280 ┬──────────── nv-split contentW ~650 ────────────┬ 宿主对话 ~660 ┐
│ 工作区/会话   │ nv-bar 36px：书名 · 阶段 · 章/字 · ⇄ ⟳ ☆ ✕     │ 消息/工具调用   │
│              ├ 文件树 280 ┬ 章节列 140 ┬ 正文 ~200 ┬ rail 44   │                │
│              │ + 工作流    │            │ 34em 限宽 │ (底部)     │                │
│              │            │            ├───────────┴────────────┤                │
│              │            │            │ 数据 / 发布 / 请求 tabs │                │
└──────────────┴────────────┴────────────┴────────────────────────┴────────────────┘
```

> 四个面（文件树、章节列、页签、rail）同时存在；正文被夹在章节列与 rail 之间，实际可用宽度最小。

### 2.6 两种通用范式在写作场景的取舍

| 维度 | 三段式（纲目 - 正文 - 检查器） | 仪表盘（Dashboard） |
|---|---|---|
| 核心问题 | “我正在写的这一章，上下文是否齐全？” | “我今天该做什么、进度如何？” |
| 最适合 | 长篇写作、修订、连续性检查 | 每日开工、多书管理、发布/数据运营 |
| 结构 | 左结构树 + 中正文 + 右上下文面板；宽度敏感 | 一个主 CTA + 进度 + 待办 + 信号 + 列表；宽度不敏感 |
| 优点 | 上下文常驻、少切页、写作沉浸 | 决策快、进度可见、首屏变化大 |
| 代价 | 需要 ≥960px 内容宽；检查器信息密度高；chrome 多 | 容易变成报表；不承载长文；数据新鲜度依赖轮询/手录 |
| 代表产品 | Scrivener、novelWriter、Novelcrafter、LivingWriter、Manuskript [S1][S15][S28][S33][S45] | Ulysses Dashboard、LivingWriter Goals、番茄数据看板、Squibler Dashboard [S6][S7][S31][S32][S47] |
| 单独使用的后果 | 首屏仍是“进入前的选择页”，第一眼变化小；窄视口下正文被挤 | 首屏变好，但进入写作后体验不变，用户仍觉得“没改到点上” |

**取舍结论**：写作场景不是二选一，而是**分层**——仪表盘负责“进入前”（今天写什么），三段式负责“进入后”（这一章怎么写），发布向导负责“写完之后”（怎么发）。这与 §6 的推荐组合一致；也是三个方案里唯一同时解决“第一眼”和“每天用”的组合。

## 3. 共性规律（8 条，每条至少 3 个产品佐证）

### 规律 1：一个结构树 + 一个正文面 + 一个上下文面板，而不是“四个导航面”

| 产品 | 做法 |
|---|---|
| Scrivener | 左 Binder 树；中 Editor；右 Inspector（元数据/快照/备注）。软木板与大纲是 Editor 的**替代视图**，不是另开一栏 [S1][S2] |
| Ulysses | 左 Library（分组/文稿）；中 Editor；Dashboard 是独立信息页，不占写作栏 [S5][S7] |
| novelWriter | 左 Project Tree；中 Document；Outline / Novel 是**视图切换**，不是常驻第四栏 [S44][S45] |
| Novelcrafter | 左 Codex/Scenes；中 Editor；右 Chat（AI 上下文面板）[S15][S16] |
| LivingWriter | 左 Chapters/Elements/Boards；中 Editor；Boards 是并列视图 [S28][S29][S30] |

**对我们的含义**：现状同时有“文件树、章节列、数据/发布/请求页签、44px rail”四个面；同类产品通常只保留**一个结构树**（在树内切换章节/设定/文件）+ **一个正文面** + **一个上下文面板**（检查器或对话）。改版的第一原则应是“减面”，不是“换皮”。

### 规律 2：写作时让 chrome 退后（专注 / 打字机 / 全屏）

| 产品 | 做法 |
|---|---|
| Scrivener | Composition Mode：全屏写作，隐藏 Binder/Inspector [S2] |
| Ulysses | Focus Mode + Typewriter Mode（当前行居中）[S9] |
| Manuskript | distraction-free 全屏模式 [S33] |
| 纯纯写作 | 专注模式（移动端极简写作）[S56] |
| Zettlr | distraction-free / 打字机模式（待验证具体入口）[S39] |

**对我们的含义**：写作视图必须有一个“专注”开关：隐藏左侧树、右侧检查器与非必要按钮，只留正文 + 字数 + 保存态；退出后恢复。否则在宿主对话窗最小 320px 的约束下，正文永远被挤压（§1.4）。

### 规律 3：大纲不是只有树，成熟产品提供“多视图”但默认只给一个

| 产品 | 大纲视图 |
|---|---|
| Scrivener | Binder 树 + 软木板（卡片）+ 大纲（表格/自定义列）[S2] |
| Plottr | Timeline（章节 × 情节线）+ Plot Grid（矩阵）+ Board（看板）[S24][S25] |
| Wavemaker Cards | 卡片 / 看板 + 时间线 + 雪花法 [S37] |
| LivingWriter | 章节列表 + 手稿板 + 规划板 [S29][S30] |
| novelWriter | Project Tree + Outline 表 [S45] |

**对我们的含义**：中文长篇的默认视图应是**卷-章-场景树**（线性推进、状态可见）；卡片/看板适合“细纲/伏笔/情节线”二次视图，不应占据首屏。方案 A 的左栏可以做成“章节树 / 细纲卡片”两个 tab，但默认树。

### 规律 4：进度与目标放在独立信息层（首页 / Dashboard），不是卡片上的两个数字

| 产品 | 做法 |
|---|---|
| Ulysses | Dashboard + Goals（写作目标、连续天数、日历；具体组成待验证）[S6][S7] |
| LivingWriter | Goals + Stats 独立页 [S31] |
| 番茄作家助手 | 数据看板：点击率 / 追读 / 完读 / 收益 [S47][S62] |
| Squibler | 项目 Dashboard（C 级来源）[S32] |
| Scrivener | Project Targets（项目/会话目标）[S2][S70] |

**对我们的含义**：管理台应从“书卡网格”升级为“今日工作台”：今日目标进度、待办（断更/待发布/门禁失败）、最近章节、数据信号。这也是方案 B 的核心。

### 规律 5：发布 / 编译是独立的多步流程，不是内容区下方的一排按钮

| 产品 | 流程 |
|---|---|
| Scrivener | Compile：选格式 → 选内容 → 设置 → 输出，多步向导 [S2] |
| Ulysses | Publishing：选择发布目标（WordPress / Ghost / Medium）→ 发布/导出 [S8] |
| Obsidian Longform | Compile：项目 → 文稿 → 输出 [S12] |
| 番茄 / 阅文 | 编辑章节 → 发布 → 审核 →（定时）[S47][S52][S53] |

**对我们的含义**：发布应改为“发布前检查 → 章节选择 → 平台与合规 → 确认与结果”的 3~4 步流程。现状发布面板不能逐章选择、没有预检清单，是任务流上最大的结构缺口 [L5]。

### 规律 6：状态语义内联在结构树 / 列表里，而不是藏在详情页

| 产品 | 做法 |
|---|---|
| Scrivener | 文档状态在 Binder 项上可见；关键词/快照在 Inspector [S2] |
| novelWriter | 文档状态 / 标签在项目树与文档头可见 [S45] |
| LivingWriter | 章节/Elements 状态在侧栏列表可见 [S28] |
| 番茄 / 阅文 | 章节列表显示审核 / 已发布状态 [S47][S53] |
| 我们的现状 | 章节行已有 ✓ 已发布 / ⚠ 门禁失败图标 [client.js:2051-2074](../../lib/client.js#L2051-L2074) |

**对我们的含义**：把“未写 / 草稿 / 待审 / 已审 / 已发 / 断更”做成树上的**文字 + 圆点**双编码（不能只靠颜色/图标），并让“下一章该写哪”在树上一眼可见。

### 规律 7：命令入口是“减少切页”的补充，不是主流程

| 产品 | 做法 |
|---|---|
| Obsidian | Command Palette（`Ctrl/Cmd+P`）+ Quick Switcher [S14] |
| SilverBullet | Command Palette + slash [S41] |
| Logseq | `Ctrl+K` 命令面板 + slash [S40] |
| Ulysses | 大量快捷键；无命令面板 [S5] |

**对我们的含义**：⌘K / Ctrl+K 适合“继续写、下一章、发布前检查、切换书籍、打开数据”；但它应建立在“主流程已经顺”的前提下，作为 P2 增强，而不是替代布局重构。

### 规律 8（中文平台特有）：发布与数据同源，写作工具只是入口

| 产品 | 做法 |
|---|---|
| 番茄作家助手 | 发布在官方 App/网页，数据看板同源；无公开 API [S47][S49][S62] |
| 阅文 / 起点 | 发布 → 审核 → 作品日报（收藏/推荐/订阅/稿酬）[S50][S53] |
| 七猫 / 晋江 | 作者后台数据 + 平台内互动（本地市场调研）[S64] |

**对我们的含义**：中文连载工作台的“数据”不能只做手工表格；必须把**发布记录、平台、章节、指标**串起来，并把“发布后观察窗”做成流程的一部分（发布完成 → 7 日观察 → 信号 → 调整）。这也是与海外写作软件最大的差异点。

## 4. 与中文长篇连载场景的匹配度

### 4.1 总表

| 维度 | 海外主流范式 | 中文连载需要 | 判定 | 改造点 |
|---|---|---|---|---|
| 结构树 | Binder / Scenes / Codex | 卷 → 章 → 场景 / 细纲；章节状态与存稿 | **直接可用，改数据模型** | 树节点增加“卷”层、字数、状态、存稿/已发；文件树降为二级 tab |
| 正文面 | 34em 行宽、Focus、Typewriter | 中文 30~42 字/行；首行缩进 2 字符；段距 0.6~0.8em；章节标题格式 | **需改造** | 中文排版预设 + 行宽按 `em` 而非固定 px；见 §5.0 |
| 专注 | 隐藏 chrome | 写作时仍要能叫出 AI 对话/门禁 | **需改造** | 专注模式保留一个“对话/检查器”浮层入口 |
| 进度 | Goals / streak / calendar | 日更字数、存稿天数、断更预警、全勤 | **需改造** | 今日目标 + 存稿天数 + 断更风险；日历热力可选 |
| 发布 | Compile / Publishing | 章节多选、平台、定时、审核、AI 声明、合规门禁 | **需新建流程** | 3~4 步发布流程 + 发布前检查清单 |
| 数据 | Dashboard | 点击率 / 7 日追读 / 完读 / 章留存 / 收益 | **需改造** | 指标卡 + 趋势 + 信号（复用现有 `metrics`/`signals`） |
| 检查器 | Codex / Lorebook / Inspector | 一致性 / 合规 / AI 痕迹 / 伏笔 / 门禁 | **需改造** | 右检查器分区：门禁、审计、AI 痕迹、信号、发布 |
| 空态 | 新建项目 / 模板 | 新建书 / 导入工作区 / 从大纲开始 | **直接可用** | 首屏 hero + 主 CTA，而不是空白网格 |
| 竖排 | 无 | 中文平台阅读端横排 | **不需要** | 不实现竖排 |
| EPUB / 印刷编译 | Scrivener/Ulysses 强项 | 番茄/起点不需要 | **不需要** | 不做编译排版链 |
| 英文语法检查 | 常见 | 中文平台不适用 | **不需要** | 用中文错字/敏感词/AI 痕迹替代 |

### 4.2 直接可用（低改造成本）

1. **左纲目 / 中正文 / 右检查器**的三段式骨架（Scrivener、novelWriter、Novelcrafter、LivingWriter 均有官方布局文档）[S1][S15][S28][S45]。
2. **写作目标 + 今日进度**的信息层（Ulysses、LivingWriter、番茄）[S6][S31][S47]。
3. **发布独立流程**的交互模型（Compile / Publishing / 审核）[S2][S8][S53]。
4. **状态内联**（树上的状态点 + 文字）[S2][S45][S47]。
5. **空态给下一步**（新建项目 / 模板 / 主 CTA）[S1][S56]。

### 4.3 需要改造（不能照搬）

1. **宽度预算**：海外产品是全屏桌面应用；我们嵌在宿主槽位里，右侧还有宿主对话窗（最小 320px）。三段式必须做**自适应**：内容宽 ≥ 960px 时三栏并置；< 960px 时检查器改为右侧抽屉/底部面板，纲目树可折叠为 48px 图标条 [client.js:1025-1037](../../lib/client.js#L1025-L1037)。
2. **中文排版**：不能只给一个 `34em`。需要“平台预设”（番茄/起点/晋江）+ 首行缩进 2 字符 + 段距 + 章节标题格式；行宽以“每行 30~42 汉字”为目标，而不是照搬英文写作的 ~66 字符惯例。
3. **专注模式与 AI 共存**：中文网文作者写作时需要随时问 AI / 看门禁；专注模式不能把 AI 入口完全藏死，应保留一个浮层按钮或快捷键。
4. **进度语义**：streak/calendar 换成“今日字数 / 存稿章数 / 断更风险 / 全勤”；数据指标换成“点击率 / 7 日追读 / 完读 / 章留存 / 收益”。
5. **发布清单**：海外是“导出/编译”，中文是“平台审核 + AI 声明 + 敏感词 + 格式 + 定时”。发布前检查必须是独立清单，不能只是一个按钮 [S47][S53][S64]。

### 4.4 不需要（避免照搬）

1. **竖排排版**：中文网文平台阅读端是横排；创作端竖排只增加实现与阅读成本。
2. **EPUB / 印刷级编译**：目标平台不收 EPUB；导出 docx/txt 即可，编译链是负资产。
3. **软木板作为首屏**：卡片墙适合细纲/伏笔，不适合“每天写下一章”的线性任务；首屏应是今日任务与正文。

### 4.5 空白 / 机会（没有产品做好的）

1. **多平台发布清单**：官方工具只服务自家平台；第三方工具没有发布；开源只有番茄自动化。工作台可以做“一套稿件 → 多平台清单/差异提示”。
2. **合规门禁前置**：平台审核在发布后；工作台可以把“敏感词 / AI 痕迹 / 格式 / 字数 / 章节标题”做成发布前门禁。
3. **数据回流闭环**：发布 → 数据 → 信号 → 下一章/下一卷调整；现有产品要么只有数据，要么只有写作。
4. **断更/存稿预警**：中文连载的“存稿天数”比英文写作软件的 streak 更刚需。

### 4.6 现状任务链步数（基线，用于方案对比）

定义：从“管理工作台已打开”开始，完成“选一本书 → 写一章 → 自检 → 发布 → 回看数据”；只计用户动作（点击/按键/切换），不计输入与滚动。

| 环节 | 现状动作 | 步数 |
|---|---|---:|
| 选书 | 点书卡 | 1 |
| 选章 | 点章节行 | 1 |
| 进入编辑 | 点「编辑」 | 1 |
| 保存 | `Ctrl+S` / 点保存 | 1 |
| 自检 | 切「数据」页签 → 读信号（门禁在阅读页另一处） | 1（+阅读） |
| 发布 | 切「发布」页签 → 选平台 → 点模式按钮 | 3 |
| 回看数据 | 切回「数据」页签 | 1 |
| **合计** |  | **9** |

附带的隐藏成本：
- **3 次页签切换**（数据 ↔ 发布 ↔ 数据），每次都丢失正文上下文；
- **1 次模式切换**（阅读 → 编辑 → 阅读）；
- 发布**不能逐章选择**，只能全量未发布章提交（服务端支持 `chapters` 子集，属 UI 缺口）[L5]；
- 自检信息分散在“阅读页门禁卡”和“数据页签信号列表”两处；
- 若从会话内打开工作台，再 +1~2 步（打开工作台 / 切换工作区）。

### 5.1 方案 A：三段式写作优先（左纲目树 / 中正文 / 右检查器）

**定位**：把“写作”变成唯一主屏：左边是结构，中间是正文，右边是当前章的上下文与动作；数据/发布/请求不再是中窗下部页签，而是检查器的分区。

#### 结构图（宽屏，contentW ≥ 960）

```
宿主侧栏   ┌──────────────────── nv-split：contentW ≥ 960 ────────────────────┐  宿主对话窗
 工作区     │ nv-bar：书名 · 第N章 · 字数 · 保存态      [专注][⇄][⟳][☆][✕]     │  （保留 ≥320）

           │44  │ 纲目树 200  │ 正文（34em 居中）         │ 检查器 280~300     │
           │rail│             │                          │ ┌ 门禁 ─────────┐ │
           │ ▶  │ 卷一 ▾      │ 第38章 · 3,200 字 · ●已保存│ │ 覆盖100% 偏离0%│ │
           │ ⏹  │  ● 第36章   │                          │ ├ 审计/AI 痕迹 ─┤ │
           │ 🔗 │  ○ 第37章   │ 正文……                    │ ├ 数据信号 ─────┤ │
           │阶段│  ⚠ 第38章   │ 正文……                    │ ├ 发布 ─────────┤ │
           │状态│  ✓ 第39章   │                          │ │ ☑章 ☑平台 ☑合规│ │
           │    │             │ [保存 Ctrl+S][强制保存]   │ │ [发布前检查 →] │ │
           └────┴─────────────┴──────────────────────────┴───────────────────┘

**窄屏（contentW < 960）自适应**：

```
┌ 44 ┬ 树 48/收起 ┬ 正文 flex ┬ 检查器 → 右侧抽屉（覆盖，Esc 关闭） ┐

└────┴────────────┴───────────┴────────────────────────────────────┘

#### 首屏放什么

1. 左：当前书的**卷-章树**，默认展开当前卷，当前章高亮；每行 = 状态点 + 第N章 + 名称 + 字数/发布标记。
2. 中：**上次打开的章节**（或当前写作章）直接可写；顶部一行显示章节名 / 字数 / 保存态；门禁失败时正文上方一条琥珀色 inline 提示（不遮挡正文）。
3. 右：检查器默认展开「本章门禁」；下方依次是审计、AI 痕迹、数据信号、发布。
4. 顶部：只保留 5 个控件（专注 / 翻转对话 / 恢复布局 / 存为默认 / 关闭）；开始/停止/压缩/绑定仍在 44px rail，不新增按钮。

#### 核心任务步数（现状 9 → 方案 6）

| 环节 | 方案 A | 步数 |
|---|---|---:|
| 选书 | 点书卡（或从对话直接进入） | 1 |
| 选章 | 树中点章节 | 1 |
| 进入编辑 | **默认即编辑**（点击正文即写；自动草稿） | 0 |
| 保存 | `Ctrl+S` / 失焦保存（门禁在提交时校验） | 1 |
| 自检 | 右检查器常驻，无需切页 | 0 |
| 发布 | 检查器「发布」展开 → 勾章/平台 → 发布前检查 → 发布 | 3（展开 / 检查 / 发布；勾章与平台在面板内完成） |
| 回看数据 | 检查器「数据信号」常驻 / 或切到数据视图 | 0 |
| **合计** |  | **6** |

#### 优点

- **写作优先**：正文占据中心且宽度受保护；对话窗不再默认吞掉一半屏幕。
- **上下文常驻**：门禁、审计、信号、发布都在右栏，不用在 3 个页签间来回切。
- **结构清楚**：一个树（章节/设定/文件三个 tab）+ 一个正文 + 一个检查器，符合 §3 规律 1/2/6。
- **发布靠近内容**：发布不再是一个“表单页”，而是当前章的“下一步动作”。

#### 代价 / 风险

- **宽度敏感**：1600 视口下三栏同时出现时正文约 31 字/行；必须做窄屏抽屉与专注模式，否则会重蹈“挤”的覆辙。

- 新增：`nv-ws` 栅格、`nv-tree`（复用 `LeftNav`/`ChapterPanel` 的树与章节逻辑）、`nv-inspector`（复用 `DataPanel`/`PublishPanel`/`WorkflowPanel`）、布局预设与折叠状态。
- 估算：`client.js` +400~600 行；`smoke.mjs` 约 15~25 条断言需改/新增；`verify-visual-geometry.mjs` 需新增三栏几何断言；无新依赖。

|---|---|
| 槽位 6 席 / z-index 950 | 不变（仍在 `nv-split`） |

### 5.2 方案 B：仪表盘 + 深入（首页 = 今日工作台）

**定位**：把管理台从“书卡网格”改成“今日工作台”；点书或点「继续写」进入写作视图。首屏回答三个问题：**今天写什么 / 写到哪 / 下一步做什么**。

#### 首屏放什么

1. **一个主 CTA**：「继续写 第N章」——直接进入上次/下一待写章，不经过书卡。
2. **今日目标**：字数进度条/环 + 存稿章数 + 连续天数（中文连载语义：日更、存稿、断更）。
3. **待办**：门禁失败、未写章、发布前检查、审核中、断更风险。
4. **数据信号**：追读/完读/点击率异常，附“去看哪几章”的跳转。
5. **最近章节**：最近 5 章状态；**全部书目**降为紧凑列表（书卡网格保留在“全部书目”视图，不占首屏）。

#### 核心任务步数（现状 9 → 方案 5）

| 环节 | 方案 B | 步数 |
|---|---|---:|
| 选书 | 首屏「继续写」直达（一次点击完成选书 + 选章） | 1 |
| 选章 | 默认上次章节 / 下一待写章 | 0 |
| 进入编辑 | 进入写作视图后可写 | 0 |
| 保存 | `Ctrl+S` | 1 |
| 自检 | 首屏待办 / 写作视图门禁 | 0（首屏已显示） |
| 发布 | 首屏「发布前检查」→ 确认清单 → 发布 | 3 |
| 回看数据 | 首屏数据卡（0） | 0 |
| **合计** |  | **5**（含发布 3 步） |

> 若用户要切换别的书/章，再 +1~2 步；但“日常续写”路径是最短的。

#### 优点

- **首屏变化最大**：从“卡片 + 70% 空白”变成“一个主 CTA + 进度 + 待办 + 信号”，肉眼可辨（§6.2）。
- **最符合日更习惯**：打开就知道今天写什么，不用先找书、再找章。
- **实现风险低**：复用现有 `overview`/`detail` 数据与卡片组件；不动写作视图也能先上线。
- **为后续 A 铺路**：点「继续写」后进入的写作视图可以逐步升级为三段式。

#### 代价 / 风险

- **“仪表盘”容易变成报表**：如果只是把卡片换成统计块，用户仍要跳转；必须有一个真正的主 CTA 与可执行待办。
- **今日数据的口径**：`today` 字数需要“今日新增”而非总字数；MVP 可用本地 `lastChapter` + 发布记录 + 手工录入日期推导，缺失时显示“未录入”，不得编造。
- **多书用户**：首屏只突出“最近一本书”，其他书需要紧凑切换；不能把多书藏死。
- **写作视图不变时**：首屏变好但写作仍挤，用户可能仍判“没变”；因此建议与 A 组合（§6）。

#### 实现工作量：**S/M**

- 新增：`nv-dash` 容器、`TodayCard`、`GoalRing`（CSS `conic-gradient` 或 SVG）、`TodoList`、`SignalCards`、`BookSwitcher`；书目网格移到“全部书目”tab。
- 估算：`client.js` +250~400 行；`smoke.mjs` 约 10~15 条断言（hero/网格/搜索）需改；无新依赖。

#### 对现有守卫的影响面：**中**

| 守卫 | 影响 |
|---|---|

### 5.3 方案 C：任务流引导（选书 → 写 → 自检 → 发布 → 数据，每步一屏）

**定位**：把整条任务链做成一个显式 stepper，每步只做一件事；适合新用户、首次发布、复杂发布；不适合每天高频续写（除非提供“直接续写”快捷出口）。

#### 结构图

```
┌ 宿主侧栏 ┬──────────────────── nv-console（workflow）───────────────────────────────┐
│          │ ① 选书 ─── ② 写 ─── ③ 自检 ─── ④ 发布 ─── ⑤ 数据        [退出流程]      │
│          │ ┌─────────────────────────────────────────────────────────────────────┐ │
│          │ │ ③ 自检：第 38 章《电梯里的「在审」》                                │ │
│          │ │ 门禁：覆盖 100% · 偏离 0% · 通过 ✓   审计：1,897 字 / 5 场景 ✓      │ │
│          │ │ 一致性：2 条提示（伏笔 F-07 未回收）   AI 痕迹：B（可接受）          │ │
│          │ │ 合规：敏感词 0 · 平台规则 ✓           排版：首行缩进/段距 ✓          │ │
│          │ │ [返回修改]                                          [去发布 →]      │ │
│          │ └─────────────────────────────────────────────────────────────────────┘ │
└──────────┴──────────────────────────────────────────────────────────────────────────┘
```

#### 首屏放什么

1. 顶部 stepper：① 选书 ② 写 ③ 自检 ④ 发布 ⑤ 数据；当前步高亮，可回退。
2. 每一步只放该步的信息与一个主按钮（上一步/下一步）。
3. 第 ③ 步是“检查器聚合页”（门禁/审计/一致性/AI 痕迹/合规/排版）。
4. 第 ④ 步是发布向导：章节多选 → 平台 → 合规清单 → 确认 → 结果。
5. 第 ⑤ 步是数据页：指标卡 + 趋势 + 信号 + 下一章建议。

#### 核心任务步数（现状 9 → 方案 8）

| 环节 | 方案 C | 步数 |
|---|---|---:|
| 选书 | ① 选书 | 1 |
| 选章/写 | ② 写（默认当前章） | 1 |
| 保存 | `Ctrl+S` | 1 |
| 自检 | ③ 下一步 → 读结论 | 1 |
| 发布 | ④ 去发布 → 勾章/平台 → 确认 | 3 |
| 数据 | ⑤ 下一步 → 看数据 | 1 |
| **合计** |  | **8** |

#### 优点

- **任务链最显式**：对第一次使用的作者，“下一步做什么”零歧义。
- **发布流程最完整**：天然适合承载章节多选、合规清单、平台差异、结果回执。
- **自检聚合**：把散落在阅读页/数据页的信号集中到一屏。

#### 代价 / 风险

- **向导疲劳**：每天写一章要经过 5 个屏；高频用户会绕开。
- **编辑体验弱**：写作被放进“步骤 ②”，容易变成“填表”；长文编辑需要全屏，stepper 会占空间。
- **实现量最大**：新状态机、步骤持久化、每步的返回/脏稿守卫、发布向导；对现有 split 的复用度低。
- **与宿主对话的协同**：每步一屏时，AI 对话仍要可见/可叫出，否则写作与自检会断。

#### 实现工作量：**L**

- 新增：`nv-flow` 状态机、5 个步骤屏、发布向导、步骤持久化、跨步脏稿守卫。
- 估算：`client.js` +600~900 行；`smoke.mjs` 约 20~30 条断言；无新依赖。

#### 对现有守卫的影响面：**高**

| 守卫 | 影响 |
|---|---|
| 槽位 / z-index | 不变（仍可复用 nv-console / nv-split） |
| 控制台网格/hero | 改为步骤 ①，原有网格断言重写 |
| rail / 章节列宽 | 写作步骤可能不需要 rail/章节列，断言需按步骤分支 |
| 边界线 / 滚动隔离 | 每步一屏，滚动容器数量变化 |
| midH / tabs | 不再使用，相关断言删除 |
| measure | 写作步骤仍需 ≥420px / 34em |
| 焦点 / Esc / 脏稿 | 跨步切换必须拦截未保存；Esc 归属需重新设计 |
| 发布门禁 | 发布向导必须保留 `release_allowed` 与服务端校验 |

## 6. 推荐：B 的首屏 + A 的写作视图（分阶段）

### 6.1 推荐组合

**一句话**：用 **B** 把“打开插件”的第一屏从书目网格变成今日工作台；用 **A** 把“进入写作”后的三栏关系理顺；把 **C** 的第 ④ 步借来做发布向导；数据留在首屏与检查器，详情表格保留。

```
打开插件
  └─ ① 今日工作台（B）
       ├─ [继续写 第N章] ──────────────► ② 三段式写作（A）
       │                                   ├─ 左：卷-章树（章节 / 设定 / 文件）
       │                                   ├─ 中：正文（measure 34em，专注）
       │                                   └─ 右：检查器（门禁 / 审计 / AI / 信号 / 发布）
       │                                              └─ [发布前检查] ──► ③ 发布向导（C 的 ④）
       ├─ 待办 / 数据信号 ───────────────► ④ 数据详情（保留表格 + 趋势）
       └─ 全部书目（原卡片网格，降为二级视图）
```

**为什么不是单选**：

- 只做 **A**：管理台首屏仍是卡片网格，用户第一眼看不到变化（上一轮失败的判据之一就是“首屏轮廓没变”）。
- 只做 **B**：首屏变了，但进入写作后正文仍可能被 660px 的对话窗挤到 200px（§1.4），日常写作不顺。
- 做 **C**：任务链最清楚，但每天写一章要过 5 个屏，向导疲劳；它更适合作为“发布子流程”，而不是主界面。

### 6.2 为什么这次会“一眼看出变了”（逐条对照上一轮失败判据）

上一轮（UX-061 A+B）的交付集中在令牌桥、对比度、输入框盒模型、字数行宽、rail 44px、书脊线、字号 ±0.5~1px 等**基础设施与小修**，没有改变信息架构、页面骨架与任务流（来源：[UX-061 设计文档](../design/UX-061-visual-directions.md)）。本轮组合方案的可见差异：

| 判据 | 现状（截图/代码事实） | 组合方案 | 用户可见差异 |
|---|---|---|---|
| **首屏轮廓** | 书卡网格 + 新建磁贴；1600×900 下约 70% 空白 [L9] | 今日工作台：一个主 CTA + 今日目标 + 待办 + 信号 + 最近章节 | 第一眼不再是“卡片墙”，而是“今天要做什么” |
| **空间优先级** | 正文 ~200px，对话 ~660px（1600 视口）[L7] | 写作预设：chat 320~380、树 200、检查器 280；正文 ≥420px，宽屏 34em | 正文从“最窄”变成“主角”，对话退到辅助位 |
| **导航面** | 文件树 + 章节列 + 3 个页签 + rail = 4 个面 [L1] | 一个树（章节/设定/文件 tab）+ 正文 + 检查器（+ rail） | 入口减少，视线不再四处跳 |
| **任务流** | 3 次页签切换；发布 = 一排按钮；不能逐章选 [L5] | 0 次页签切换；发布 = 检查器入口 → 3 步向导（章节多选/平台/合规/确认） | 写作与发布连成一条线 |
| **状态表达** | 书卡 chip、rail 竖排短标签、章节 ✓/⚠ 图标 | 树上的“状态点 + 文字”（未写/草稿/待审/已审/已发/断更）+ 首屏待办卡 | 状态从“装饰”变成“下一步动作” |
| **视觉层级** | 多个同权按钮/页签；面板标题≈正文 | 首屏 1 个主 CTA；检查器分区标题（门禁/审计/信号/发布）；写作视图只保留 5 个顶栏控件 | 有明确的第一、第二、第三视觉层 |

> **验收方法**：把改版前后同视口（1600×900）截图并排，评审必须能**不解释就指出至少 5 处结构差异**；只能指出颜色/字号差异 = 不通过。

### 6.3 为什么更顺手（任务链与认知负荷）

| 维度 | 现状 | 组合方案 |
|---|---|---|
| 核心链动作 | 9 步（§4.6） | **5~6 步**（B = 5 / A = 6；B 的拆分为 继续写 1 + 保存 1 + 发布前检查 1 + 平台 1 + 发布 1） |
| 页签切换 | 3 次（数据 ↔ 发布 ↔ 数据） | **0 次**（检查器常驻 / 首屏卡片） |
| 选书/选章 | 每次都要点书卡、点章节 | 「继续写」直达上次章节；树里再切 |
| 自检信息 | 阅读页门禁卡 + 数据页信号两处 | 检查器一处聚合；首屏待办提示 |
| 发布 | 全量未发布章 + 一排按钮 | 逐章多选 + 3 步清单 + 结果回执 |
| 数据 | 表格 + 手工录入 | 首屏信号卡 + 趋势 + 手工录入保底 |
| 迷路成本 | 4 个导航面 + 3 个页签 | 1 个树 + 1 个检查器；当前章/当前书始终可见 |

### 6.4 分阶段落地（每阶段都可独立验收）

| 阶段 | 范围 | 工作量 | 用户当下能看到什么 | 守卫工作 |
|---|---|---|---|---|
| **P0 首屏与写作预设** | ① 管理台 → 今日工作台（继续写 / 今日目标 / 待办 / 信号 / 最近章节；全部书目降为二级）② 写作预设自动分配 chat/tree/chapter 宽度（为 P1 的 inspector 预留）③ 「继续写」记录 | S/M | 打开插件第一屏完全变样；进入写作后正文明显变宽 | 重写控制台 hero/网格断言；新增首屏布局与宽度断言 |
| **P1 三段式写作视图** | ① 左树（章节/设定/文件 tab）② 中正文默认可写 + 专注 ③ 右检查器（门禁/审计/AI/信号/发布）④ 去掉中窗下部 3 页签 | M | 写作视图变成“树 / 正文 / 检查器”，不再有页签来回切 | 重写 tab/midH/左窗断言；新增三栏/抽屉几何断言；保留 rail/measure/焦点 |

| **P3 命令与细节** | ⌘K / Ctrl+K（继续写、下一章、发布前检查、切书）；快捷键；空态；中文排版预设（番茄/起点/晋江） | S | 键盘可达；新手知道下一步；排版更像平台 | 焦点/快捷键/i18n 断言；不新增宿主耦合 |

> 顺序理由：P0 的“可见变化 / 成本”性价比最高，先拿到用户“确实变了”的反馈；P1 才是真正的写作面重构；P2 把发布闭环补上；P3 是效率与打磨。P0 不依赖 P1，可先上线。

### 6.6 风险与对策

| 风险 | 表现 | 对策 |
|---|---|---|
| 宽度仍然不够 | 三栏在 1600 下正文 < 420px | 写作预设强制 chat ≤380；contentW < 960 时检查器改抽屉；专注模式可收起树/检查器 |
| 首屏变“报表” | 卡片换成统计块，仍要跳转 | 每个卡片必须有一个动作或跳转；主 CTA 只有一个；待办可点击直达章节 |

| 测试大面积翻红 | smoke 字面断言与新 DOM 不符 | 布局改动与 smoke/探针同 commit；先加新断言再删旧断言；不“只改 CSS” |

| 检查器过密 | 280px 塞 5 个分区 | 默认展开“门禁 + 发布”，其余折叠；摘要行 + 详情展开 |
| 与宿主对话抢空间 | 用户把对话拖大后又挤 | 写作时记住“写作预设”；切回对话布局时恢复；提供一键“专注写作” |
