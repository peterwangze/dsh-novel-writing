## 一、V-1 控件高度令牌 → **落地成立；两档语义需统一定义（P2，非阻塞）**

**我实测的消费者**（`var(--nv-ctl-sm|md)`）：
| 令牌 | 消费者 | 数量 |
|---|---|---|
| `--nv-ctl-sm`（28px） | `.nv-csortbtn`（排序钮）/ `.nv-cfold`（折叠钮）/ `.nv-cbtn` / `.nv-cbtn-accent` / `.nv-wfctl-btn` / `.nv-wfctl-btn2` | **6** ✅ |
| `--nv-ctl-md`（32px） | `.nv-cinput`（输入框） | **1** ✅ |

smoke 断言 `ctlSm >= 3 && ctlMd >= 1` 为真实消费计数（非「定义了就算」）✅。**两档 28/32 与设计规格的数值一致**。

但**层级关系与设计文档 §2.1 不一致**，且存在一处可见风险：
- §2.1 原文：`28（密集区/头部）、32（主控制条）`；实现是「**按钮 28 / 输入 32**」——其中 `.nv-wfctl-btn`/`.nv-wfctl-btn2` 恰恰是**主控制条按钮**却拿了 28 ⇒ 规格与实现口径冲突。
- **同排高度差**：`lib/client.js:3794`（`.nv-cinput` 32）与 `:3801`（`.nv-cbtn` 28）在同一个创建对话框行里相邻 ⇒ 同排控件 4px 高差，观感风险真实存在。

**裁决**：令牌化本身成立（V-1 目标达成），但要**收口为一条口径**（二选一，随 1b-2 或目检后 1 行修复）：
- **推荐**：表单行按钮与输入框同档 → 给 `.nv-cinput` 所在表单行的按钮补 `min-height:var(--nv-ctl-md)`；紧凑/图标/排序/折叠类保持 28。这样「28 紧凑 / 32 表单行」语义清晰，且两档都有真实消费者。
- 或：把 §2.1 的「32 = 主控制条」改为「32 = 表单行输入与同排按钮」，并在 §7.4 写死该映射（**文档改，不动代码**）。
- 无论哪条：**G-5 目检必须覆盖「创建/请求表单行」与「工作流控制条」两处高度观感**。

## 二、V-2 尺度字面量 → **归零/白名单成立；映射方向接受；命名语义与换行风险需登记**

**实测**：CSS `font-size` 字面量 **48 → 9**；9 处逐一核对全部落在图标/字形选择器：`.nv-drawer-title-ico`(16) / `.nv-console-title-ico`(18) / `.nv-csearch-icon`(16) / `.nv-cplus-icon`(20) / `.nv-bar .nv-mini`(14) / `.nv-console-head .nv-mini`(13) / `.nv-cico`(13) / `.nv-bar-ctl`(16) / `.nv-ccard-mono`(20，书名首字装饰块)。
smoke 新增 `ICON_FS_SELECTORS` 白名单断言，且**提取口径 fail-closed**（行首不是 `'selector{` 形态 ⇒ 记为 `?` ⇒ 不在白名单即红）✅。

**映射裁决（39 处）**：
- 10 / 10.5 → 11（caption）、11.5 / 12 → 12（base）、13 → 13.5（card）、14 / 15 → 15（body）——相对 7 档规格（11/12/13.5/15/17/20/28）**都是就近归入**，方向正确 ✅。
- **+0.5~1px 的观感代价：接受**（不是回退）。理由：①这些值原本就是尺度外噪声，归入最近档是治理而非美观妥协；②中文 10/10.5px 在 100% 缩放下本就可读性不足，+0.5~1px 是净改善；③回退并登记豁免会让「尺度唯一来源」重新出现例外，代价大于收益。**条件**：G-5 目检必须专项检查**固定宽控件是否因 +1px 换行**（重点是 `.nv-chip` / `.nv-csortbtn` / `.nv-wfchip` / 书卡 meta 行），若出现换行再按单点豁免处理（豁免须写明理由与取值）。
- **P3 命名语义漂移**：`--nv-fs-card` / `-chapter` / `-stat` 是**角色名**，现在被当作**字号档**用于通用文本（如 13.5 档用于非卡片文本）。建议后续把令牌名改为档位名（如 `--nv-fs-13_5`）或至少在设计文档 §7.4 注明「`fs-*` 按字号档使用，角色名为历史别名」。不阻塞。

## 三、V-3 泛化裁决 → **接受泛化**（Developer 的判断正确，我的原裁决口径不够）

- **事实核验**：`TK.text3` 已改 `--nv-fg-muted`；`--nv-fg-subtle` 现 **6 处 = 1 定义 + 5 非文本**：`lib/client.js:2115`（状态图标色）/ `:4807`（抽屉 caret 图标）/ `:4829`（`.nv-dot` 边框）/ `:4961`（搜索清除图标）/ `:5034`（`.nv-cdot::before/after` 边框）——**文本用法 0 处** ✅。
- **裁决：接受「全部文本改 muted」**。依据：WCAG 1.4.3 的 4.5:1 适用于**所有普通字号文本**，与是否 <12px 无关；设计文档原先写的「≥12px 或非信息性」豁免本身不成立（12px 3.71:1 仍违规）。Developer 的泛化是**纠正了设计文档的错误豁免**，不是越权——我 DR2 只点名 3 处是**抽样不足**，泛化才是正确收敛。Developer 主动上报要求裁决的做法符合流程。
- **接受后的口径变更（已由 §7.5 落地，我确认其准确）**：`--nv-fg-subtle` 重新定义为**仅非文本**（图标/状态点/边框/分隔线）；文本最低层级 = `--nv-fg-muted`（亮 5.80 / 暗 10.42）。
- **附条件**：①三级文字色关系变为「primary / muted」两级 + 「非文本 subtle」，后续若需要第三级文本，MUST 用**字号/字重**区分而非降低对比度；②若确需新第三级色，MUST 交由 Design Reviewer 裁决并给出可测下限（§7.5 已写，认可）。
