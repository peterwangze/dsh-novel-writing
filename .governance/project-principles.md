# 项目原则（canonical source）

> 本项目（dsh-novel-writing）的**品质原则与编程要求**权威源。会话强制注入面 = `AGENTS.md` 的「项目级原则」节（本文件内容一致；AGENTS.md 仅 Governance Bootstrap 段由模板管理，自升级保留其余节）。
> 应用范围：本仓库的一切分析、实现、修复与交付（含 agent 预设、宿主插件、客户端、安装通道、文档）。
> 引入时间：2026-08-22（DEC-011）；任务记录：GOV-001。P-08 追加：2026-08-28（DEC-016，用户直接要求「禁止自造轮子」）；任务记录：GOV-002。

## 一、分析与实现原则

| ID | 原则 | 执行要求（检查点） |
| --- | --- | --- |
| P-01 | 分析和推演需要基于事实，不允许假设和编造 | 任何分析以文件、命令、测试、日志、用户明确输入或外部文档为事实依据；无法证实的结论标 `BLOCKED` / `待验证` / `未知`，禁止推测性陈述为事实 |
| P-02 | 实现需要进行全面的分析，避免修改遗漏 | 动手前穷尽受影响面：调用方/消费方、配置、契约、文档、测试、安装/升级路径；逐项核对后再开工 |
| P-03 | 实现需要考虑对原有功能的影响，避免引入新问题 | 变更前做回归核对清单（门禁/工具/工作台/预设/发布通道/CI）；对既有行为逐一确认不回归 |
| P-04 | 实现需要进行测试看护，构建防护网，避免后续问题反复 | 任何实现必须配套验证：`node --check` + `validate-preset` + `smoke`（行为级）+ CI；发现即补回归测试；验证结果入证据 |
| P-05 | 实现需要考虑泛化性，严禁单点修改 | 修复放在正确的抽象层；同类问题全局排查（如守卫式 hook、防连点、路径校验需全文件/全模块扫描后统一处理） |
| P-06 | 以高质量交付为准则，严禁为了完成任务而忽略质量 | 禁止缩水验证、跳过审查、以「能用」替代「正确」；质量门禁（评审/测试/契约核验）为硬性环节 |
| P-07 | 修复要保证安全性，避免引入导致损坏用户数据的情况 | 路径注入/CSRF/回环/权限边界复核；落盘原子化、防覆盖、防重复执行；涉及用户数据（书目/稿件/状态/配置）的路径必须有无损验证 |
| P-08 | **禁止自造轮子：有现成的开源参考与免费资源时优先使用，严禁自己造轮子** | ①动手前先调研：同类功能是否有现成开源实现/插件/组件/素材（GitHub、npm、宿主既有能力、参考项目源码）可参考或直接复用（如 dsh-worktable 的引擎/样式/交互范本、宿主 `--dsw-alias-*` 令牌体系、emoji/开源图标、参考项目已解决的技术点）；②「先抄对，再优化」：把参考项目的已验证逻辑作为起点，禁止凭印象重新发明（如坐标/几何、请求链、门禁语义等已有成熟做法）；③明确免责边界：复用前确认许可（MIT/Apache 等）与依赖面，不引入未核验的第三方；④自查问题：本任务是否在重复造宿主/生态已提供的能力？若「新造的」与现有能力重叠，停下说明并换复用方案；⑤审查门槛：Code Review 与自查清单新增「是否自造轮子/是否有更省时间的现成替代」核对项 |

## 二、编程要求

| ID | 要求 | 执行要求（检查点） |
| --- | --- | --- |
| C-01 | 设计需要考虑可扩展性和可维护性，需要基于未来进行设计 | 接口预留演进空间；避免一次性特设；新方案先问「下一个变更会怎么长」 |
| C-02 | 实现需要避免架构腐化，避免引入架构问题和可维护性问题 | 分层与依赖方向不破坏；事实源单一（不出现同一事实多份权威）；发现腐化趋势即记 risk |
| C-03 | 实现需要保证模块/类/接口的职责单一，避免引入上帝类/上帝模块和多功能接口 | 职责膨胀即拆解；新代码不把多职责塞进现有大函数/大对象；接口契约专注单一用途 |
| C-04 | 实现不要搞任何冗余的修改，保持修改的纯粹性 | 每个文件的每处改动服务于本任务；顺带发现问题 → 记新任务，不在本任务内夹带无关修改 |
| C-05 | 一个 commit 承载一个问题修改/功能实现 | commit 与 task ID 一一对应；跨任务变更拆 commit（git 分批暂存）；同一 commit 内治理记录与产品代码需同主题 |

## 三、应用机制

- **会话启动**：AGENTS.md 注入（本文件同行），每次会话生效。
- **任务入账**：涉及实现的 task 在 plan-tracker 入账时，P-02/P-03/P-04/P-05 作为默认验收项。
- **审查门槛**：Code Review 清单必须包含 P-03（回归）、P-05（泛化）、C-03（职责单一）、C-04（修改纯粹性）、C-05（commit 原子性）核对项。
- **证据要求**：产品代码 evidence 的「结构化事实」须含测试命令与结果（P-04）；修复类 task 证据须说明安全与数据无损核验（P-07）。
